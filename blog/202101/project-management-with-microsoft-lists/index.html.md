## 前言：專案管理工具的抉擇

其實 Jira、Notion 是更好的專案管理工具(個人使用後的觀感)，但因為許多公司都有購買 Office 365 來使用 office、excel… 等工具，所以如果專案管理也能用 Office 365 來解決不但能節省一筆經費，更可以**讓團隊把注意力集中操作同一個軟體，而不是做一件事都需要更換一個軟體**。

Office 365 裡比較適合拿來做專案管理的有 Microsoft Planner 、 Microsoft Lists 這兩個，如果有興趣了解兩者的不同可以[參考這篇文章](https://deanlin.net/blog/202010/microsoft-planner-vs-lists/)，但經過考量後 Microsoft Lists 更為適合多個單位之間的合作，下面會詳細介紹我是如何使用的。

## 一、建立符合專案管理需求的 Lists

### SETP 1: 建立空白清單

  這裡你可以選擇建立符合自己需求的空白清單

  依據專案的需求自行填寫

### SETP 2 : 依照需求新增欄位

➤ 下面說明每個欄位的作用，可依自己的需求再做調整：

- **任務名稱**：簡單明瞭讓被指派的人員初步了解任務
- **描述**：詳細說明任務內容，如果有子任務建議使用條列式呈現
- **進度**：顯示該任務完成進度，此欄位會因為任務類型的不同而有不同的文字呈現
- **優先度**：分成 緊急>普通>不重要 3 種
- **負責人員**：PM 指派的任務對象，此欄位可選擇群組或是由多個人負責
- **相關人員**：除了負責人員外，需要追蹤該任務的人員，就像是信件的副本概念
- **負責 PM**：通常就是建立該任務的 PM 本人
- **任務類型**：分成 文件、設計、程式、測試 4種，方便透過此欄過濾出想要的資訊
- **相關連結**：可能是要測試的網址、給設計的參考範本、完成的文件連結…
- **開始日期**：被指派的人員開始作業時的時間
- **到期日**：完成該任務的時間

## 二、模擬專案實際情境

需求：今天有一個網站需要新增一個商品清單頁面，並且在這個頁面可以對商品進行新增、修改、刪除、查詢的動作

### 前期

指派設計完成 wireframe，同時 PM 分析這個頁面的細部需求規格

### 中期

在設計的 wireframe 與 PM 的需求規格完成後，後端工程師可以依據需求規格開始撰寫 api ，前端工程師也能依照 wireframe 先完成畫面等 api 完成後串接

### 後期

在前端工程師依照 wireframe 完成 UI 並串接好後端 api 後就可以請測試部門做功能上的確認，測試的功能項會建議由工程師做簡易的文件撰寫。

測試後依據測試結果將進度轉為 **測試成功、測試失敗 ，**如果測試失敗要說明原因並重新指派給當初負責的人員處理。

## 三、操作上的小訣竅

### 善用篩選功能找出需要的資訊

因為列表上的資訊非常多，所以我們可以依據實際的情境來做調整：

- 將 **優先度度為緊急 **的篩選出來確認進度
- 測試人員只需要瀏覽 **任務類型為測試** 的就好
- 可以 **用關鍵字搜尋任務名稱**

### 使用交談功能討論任務進度

使用過本產品的人我想最大的詬病之一就是文字圖片無法複製貼上，目前看到可以複製貼上的區域只有 **任務裡面的交談**，如果你們有很多詳細的內容是寫在交談裡面的請記得在描述中說一下，不然大家都不知道交談裡面有更多內容。

## 結語：讓工具連結發揮更大功用

如果只操作 Lists 你會感覺到有些部分綁手綁腳的，但 Office 365 的工具我想當初設計的想法就是要使用者把裡面的工具互相串聯吧？所以每項工具只做出基礎的功能，如果要更深入的功能需要再與其他工具結合：

- 如果你要 subtask 的功能要與 Microsoft Planner 結合
- 想要撰寫更詳細的文件內容就直接超連結到 Microsoft Office

他不是一款完美的工具，但使用者可以透過其他方法讓他更好用。
